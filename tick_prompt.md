# Tick Prompt — Stonks (Consolidated MVP)

**Market tick received.** Each tick is a separately spawned session, not one long-lived warm conversation — nothing is "already in context" by default. Follow this loop:

## Core Loop

1. **Read strategy.md, params.json, and decision_heuristics.md** → fresh, every tick, no exceptions. They're small; the read is cheap. Correctness > saving a few tokens.

   Before trading, run `python3 scripts/workspace_review.py --gate` (see `skills/workspace-review.md`). If it reports critical findings (`state/.workspace_blocked` set), **do not trade this tick** — note the reason in active.md and `HEARTBEAT_OK`. Warnings alone don't block; just carry them into active.md so they don't go unnoticed.

   Also call `memory_search("<today's regime> <top watchlist/position tickers>")` once — feeds the recall store dreaming promotes from. Skip only on tool error, never block the tick.

2. **Read active.md** → `read strategies/active.md` — decisions, watchlist state, regime notes from last tick. **Position data (prices, P&L, share counts) is NOT in active.md** — query it on demand: `get_self_stats` for account-level P&L and `get_quotes` for live prices. Active.md is for what you did and why, not stale snapshots of what things cost. **Active.md is a log, not an authoritative data source** — if it records a decision that was explicitly conditioned on a stale regime/ceiling/signal, reconsider it with today's fresh data from steps 4-5 before executing it blind. The live `get_market_regime` call (step 5) overrides any regime-dependent conclusion written in an earlier tick's active.md entry.

3. **Read watchlist** → `python3 scripts/trader_query.py watchlist` — your growing/shrinking list of small-cap candidates. This is your discovery mechanism for this MVP (no ML, no news-source aggregation yet — just this).

4. **Check portfolio** → executor status check, see `skills/tool-invocation.md` — only source of truth for cash/positions/P&L, never the data bus. Its output now also includes a `deployment_pressure` block (cash_pct, consecutive under-deployed ticks, and research-escalation flags) — read once here, referenced by steps 7 and 8 below. Zero extra cost: it's computed from the same account fetch, not a second call.

   Its output also now includes a `gate_status` block — current per-sector open-position counts vs `risk_guards.max_positions_per_sector`, the daily order count vs `risk_guards.order_count_audit_threshold_daily` and whether that gate is even enabled, and the open-position count vs `risk.max_positions` (and whether that gate is enabled). **Treat this as authoritative for this tick, overriding anything you recall from your own prior reasoning or a previous tick's rejection message** — a sector or limit that was "FULL" several ticks ago may not be anymore (params.json changes without a code deploy). Confirmed 2026-07-31: a stale remembered "2/2 sector cap" gated a real candidate for 29 consecutive ticks after the actual cap had already been raised to 5 — this field exists so that specific failure can't recur. Referenced by step 8's sector/position-count reasoning below; don't recompute or recall those numbers there, use this block.

5. **Market snapshot (best-effort)** → data bus per `skills/data-bus-fallback.md` for quotes/momentum/fear-greed; sentiment is separate — read `state/sentiment_cache.json` per `skills/sentiment-cache.md` (refreshed independently every ~15min, not fetched live per tick). Skip either if stale/down/missing, never block the tick.

   Also call `get_market_regime` and `get_risk` (MCP tools, not the REST curl) — real regime/risk data, not a price-action guess. Skip on error, same as everything else here.

   Once per day only (first tick after 09:30 ET, or if active.md shows no macro entry yet today): call `get_macro` too — yield curve/CPI/FOMC context doesn't change tick-to-tick, no need to re-fetch every 5 minutes.

6. **Scan positions near triggers** → run `python3 scripts/executor.py --account stonks --action check-stops` — mechanically checks every open position against the hard stop (`risk.stop_loss_pct`, fixed floor) and trailing stop (`risk.trailing_stop_pct`, ratchets up from peak price since entry). Also checks the oversized-position cap (`risk.max_position_pct` — a position that's grown over cap via price appreciation, not a new buy). Any ticker returned in `breaches` **must** be sold this tick via step 9, no re-litigating — for `stop_type: "oversized"`, sell exactly the `shares_to_sell` count given (a trim, not a full exit) unless another breach on the same ticker calls for a full exit instead. Also check profit targets, thesis breaks — for names near a trigger, `python3 scripts/trader_query.py positions --ticker <X>` to check the stored thesis.

   **Fast-path check (`decision_heuristics.md`)**: before triaging a breach/thesis situation from scratch, scan the file's `Active` nodes for a clean match. A clean match hands you a fast recommended action — cite it explicitly in `active.md` as `[tree:<node-id>]` and default to it unless you have a concrete stated reason not to. No match, an ambiguous match, or a stated reason to deviate all fall through unchanged to the judgment call below — this is a prior, not a gate. Never force-fit a partial match to a node's action.

   **`stop_type: "long_play_resolved"` is the one exception — not a sell signal.** It means a long play's `predicted_by_date` arrived (mechanically resolved right there in `check_stops()`, logged to training data automatically — nothing for you to do about the resolution itself). `long_play_hit`/`loss_pct` tell you whether the prediction was right. The position has now reverted to the normal trailing-stop schedule and should be judged like any standard HOLD/SELL decision from here — the breach itself doesn't obligate a sell.

   **Conviction/long plays are exempt from `decision_heuristics.md`'s `market_context_exit_v1`** (2026-08-03) — that judgment layer (SPY fade → trim a >2%-up position) applies to standard positions only. For an open `conviction_play`, or an active (unexpired) `long_play`, skip that check entirely — the hard stop and the position's own (wider) trailing stop from `check-stops` above still apply unconditionally; only the per-tick market-context judgment is skipped.

   **Daily thesis re-confirmation** (2026-08-03, conviction/long plays only, first tick after 09:30 ET or whenever `thesis_last_checked_at` isn't today's date): `python3 scripts/trader_query.py positions --ticker X --with-history` to read the recorded `thesis_claim`/`thesis_invalidation`/`thesis_entry_signals`. Re-run `record_decision.py reconcile` with fresh `--features` and compare against `thesis_entry_signals` — has a signal reversed? Check current reality against `thesis_invalidation` — has that specific condition happened? (for an index-anchor position, score `regime`/`macro`/cross-index `technical` signals here, not per-company ones — see `decision_heuristics.md`'s `index_anchor_entry_v1`/`index_anchor_thesis_break_v1`) Write the verdict: `python3 scripts/trader_write.py position-update-thesis --ticker X --verdict intact|weakening|broken --note '...'`. `intact`: nothing else to do. `weakening`: note it in active.md, no forced exit — two consecutive `weakening` verdicts is a reasonable prompt to reassess more carefully, not an automatic trigger. `broken`: sell it in step 9, `--close-reason 'thesis broken: <the specific condition that occurred>'`. Bounded to ≤7 checks/day (max concurrent conviction + long plays) — cheap, don't skip it for named positions that qualify.

   **Bootstrap-phase check**: `python3 scripts/trader_query.py bankroll` once — if `ceiling` is below `params.json: bootstrap_phase.ceiling_threshold`, apply the quick-exit bias (`params.json: bootstrap_phase`) to any open position sitting at or above `bootstrap_phase.quick_exit_min_return_pct`: bank it in step 9 rather than holding for the full profit target. Skip this check once ceiling clears the threshold.

7. **Discovery pass** → run `python3 scripts/merge_discoveries.py` unconditionally, every tick — mechanically merges any unconsumed `discoveries/*.md` candidates into the watchlist (idempotent, no-op if nothing new). Don't rely on remembering to do this manually; the script exists because that failed for days.

   Then run `python3 scripts/promote_candidates.py` unconditionally, every tick — pulls the top fresh (in-band, not stale) candidates out of the continuous `discovery_daemon.py` scanner's pool (`state/discovery_pool.db`, a real systemd-supervised background process, not a cron — always rotating through the tradable universe) into the watchlist, same dedup/`max_size` contract as the merge above. Idempotent, no-op if the pool has nothing new or fresh enough — zero real cost either way, this is a local SQLite read.

   Then check `python3 scripts/trader_query.py watchlist` — the merge above may not have refilled it. **If it's empty**, don't wait for the 45-min `stonks-discovery-urgent` cron: run `python3 scripts/discovery_urgency_check.py` right now. Its empty-pipeline check fires regardless of cash deployment, so it'll run a fresh scan and write straight to `discoveries/*.md` immediately — next tick's merge step picks the results up automatically. This is the only branch of step 7 that costs a real API call; skip it whenever Candidates already has entries — don't run it "just in case."

   Otherwise, light touch: anything exhausted (evaluated many times and never worth a position, or just old — see `watchlist.max_evaluations_before_drop`/`max_age_hours_before_drop` in `params.json`)? `python3 scripts/trader_write.py watchlist-drop-stale`. Noticed a new name worth watching from your own scan? `python3 scripts/trader_write.py watchlist-add --ticker X --note '...'` — the merge above only covers probe-discovery's output, not your own noticing.

   **Escalating research under sustained pressure**: step 4's `deployment_pressure` block also reports `escalate_freeform_research`/`escalate_backtest_check`. If `escalate_freeform_research` is true, run the `freeform-discovery` skill this tick in addition to its normal 8am cadence (news/catalyst hunting, not a trading action), then run `python3 deployment_pressure.py --mark-escalated freeform` so it doesn't refire every tick. If `escalate_backtest_check` is true, run `python3 scripts/replay_check.py` directly (same script `stonks-research-loop`'s nightly cron uses) and mark it with `--mark-escalated backtest`. Both are gated by persistence (~3hrs / ~1 trading day of sustained under-deployment) and their own cooldowns — don't run either "just in case."

8. **Decide** → BUY/SELL/HOLD with structured JSON, one entry per ticker considered. Keep rationale tight. **Use step 4's `gate_status` block for any sector-cap/order-count/position-count reasoning here — don't recompute or recall it**; it's the fresh, authoritative number for this tick. Remember the mandate: **small-cap, wide and diverse** — many small positions over concentrated bets, no hard cap on position count (v1.6). **Doing nothing is a cost.** Before deciding HOLD, if `deployment_pressure.cash_pct` (step 4) is at or above `watchlist.discovery_urgency.cash_threshold_pct`, evaluate at least one probe-size BUY (`risk.probe_position_pct`% of portfolio, floor 1 share — `scripts/position_sizing.py --tier probe --price <price>`) before writing HOLD for the tick. This is "widen the funnel," not "force a trade regardless of gates" — the full gate chain (bankroll ceiling, sector concentration, portfolio risk, cash, hours) still runs unchanged, and a probe that gets correctly gated off is a **pass**, not a failure to fix. Log the attempt and why it was or wasn't gated in `active.md` either way, so a string of correctly-blocked probes stays visible rather than looking identical to not trying.

   **New-entry candidates are evaluated in a bounded rotation, not the whole watchlist every tick** — evaluating the full watchlist every tick blows the cron's execution timeout: use `python3 scripts/trader_query.py watchlist --batch N` (`params.json: watchlist.eval_batch_size`, least-recently-evaluated first) instead of the full list from step 3/7 for this new-entry check. After deciding on that batch (BUY, gated, or nothing qualified — doesn't matter which), run `python3 scripts/trader_write.py watchlist-mark-evaluated --tickers <comma-separated batch tickers>` so the rotation advances — every candidate cycles through over several ticks instead of getting re-scanned from scratch each time. This bound applies only to *new*-entry watchlist screening; position management (step 6) and scaling-into-winners (below) stay exhaustive since the position list is naturally small.

   **Exit**: fixed stop-loss/trailing stop/profit-target are mechanically enforced (`params.json: risk`, `executor.py` check-stops, step 6 above) — MACDh-flip is NOT a mandatory exit as of v1.13, only a near-zero-oscillation noise filter. Situational exit calls (peaked-pump restraint, market-context trim, thesis break) are `decision_heuristics.md` nodes, checked in step 6/8's fast-path above. Read strategy.md and decision_heuristics.md fresh each tick — don't carry forward last tick's rule set from memory.

   Note: scale-into-winners (v1.7) was reverted in v1.20 (strategy.md's "What I'm Learning") — it actively degraded Sharpe. Do not scale into an existing position; a new entry or nothing, same as any other tick.

   **Fast-path check before full synthesis**: for a new-entry candidate or a decision that resembles a known pattern, check `decision_heuristics.md`'s `Active` nodes first for a clean match. A clean match returns a fast recommended action **and tier/sizing guidance** — apply it by default, citing the node id (`[tree:<node-id>]`) in `active.md` and `--rationale`; you may still override with the full gestalt reasoning below if you have a concrete, stated reason — same non-negotiable "state why" posture as any other judgment call in this step, never a silent override. Anything that doesn't cleanly match falls through unchanged to the full synthesis below, at `probe` tier. A `Watch`-tier match carries no recommended action — it's a cue for *extra* scrutiny, not a shortcut; log it the same way with no action taken.

   **Before entering any new position, reason over the gestalt, don't run a checklist.** Pull together: `get_insiders` (Form-4 filings), `get_fundamentals` (P/E, ROE, analyst target — `skills/fundamentals.md`), `get_congress` (Senate/House disclosures, last 1-2 weeks — silence means no recent disclosure, not "nothing to see"), `get_social` (Reddit/StockTwits/Bluesky, real retail chatter — `skills/social-sentiment.md`, read the actual posts, don't just trust the aggregate score), `wiki_search` on both the ticker and its sector/theme (durable knowledge, yours and other agents', including `stonks-worldview-sync`'s standing sector/macro narratives — a per-ticker-only search misses those), `get_ml_signal` (trained win/loss classifier probability plus a plain-language explanation, from the ML training service once it's publishing — treat as the newest, least-proven signal), and cross-sectional momentum rank (`skills/data-bus-fallback.md`'s `/momentum`). None of these individually gates a trade — RSI/volume/regime are signals to weigh, not a checklist to clear. The point is synthesis: a world narrative and a congressional trade pointing the same direction is stronger evidence than either alone, and worth saying so explicitly in the rationale. Skip `get_technical_scan` (paywalled) and `get_flow` (disabled — not real options flow data). These are heavier calls, so spend them on names you're actually about to buy, not the whole watchlist every tick. Skip any that error — none of these block a trade, they only inform it.

   **A catalyst-led entry doesn't need a technical green light.** In practice this has collapsed to a MACD/RSI/volume checklist despite the paragraph above — watch for that pattern in your own recent batches (a string of `MACDh negative ❌`/`near-zero MACDh ❌` rejections with no mention of news, fundamentals, or the ML signal is the tell) and correct for it explicitly. A real, fresh catalyst is enough on its own to justify a small probe: `sentiment`/`news_headline` are now populated directly on each watchlist candidate (no extra fetch needed) — a candidate with a real, specific (not generic/boilerplate) headline and `|sentiment| >= 0.5`, priced in a reasonable band, and not already extended >20% above its 20-day MA, is a probe-worthy setup even with a flat or mildly negative MACDh. Size it small (probe tier, same as any other probe) and say in the rationale that this is a catalyst-led entry, not a technical one — that framing is itself scorecard-relevant. This is not a second checklist to replace the first; it's permission to act on strong non-technical evidence without waiting for technicals to agree.

   **Catalyst-liquidity gate is mechanized (v1.18, 2026-08-05)**: for a sub-$500M catalyst-led candidate, pass the market cap and average daily dollar volume you already pulled from `get_fundamentals` as `--market-cap`/`--avg-dollar-volume` on the BUY call (step 9) — `gate_catalyst_liquidity` in `executor.py` will block the order if avg dollar volume is under $50K/day, no extra research call needed. The gate fails open (doesn't block) if these flags are omitted, so it only actually protects you if you pass the data you already have.

   **Conviction is a real score, not a guess**: score each signal you actually checked into `--features` JSON (per `skills/self-improving-agent.md`), then run `python3 scripts/record_decision.py reconcile --features '...'` and use its `combined_confidence` as the conviction you pass to the executor call (step 9) — that single call now also writes the decisions-table row (mechanized, no separate post-trade logging call needed). `params.json: risk.conviction_floor` is a sanity check (catches a broken/zero score), not a bar to clear — real entry quality comes from the gestalt above, stated honestly in the rationale. You may still deviate (size up/down) if you have a concrete reason not captured in a scored signal — say why in `--rationale`; that disagreement is itself scorecard-relevant, same as the existing echoed-back `reconciled` framing already documents.

   **Two capital buckets, pick one per entry** (`params.json: risk.long_play` / `risk.conviction_play`). Eligibility/exit conditions for conviction and index-anchor plays are `decision_heuristics.md` nodes (`conviction_play_anchor_v1`, `index_anchor_entry_v1`, `index_anchor_reallocation_v1`, `index_anchor_thesis_break_v1`) — check those first per step 8's fast-path check above, don't re-derive the eligibility bar from scratch here. CLI syntax:
   - **Standard**: the wide/fast opportunistic sweep, most of the book — no special tag needed.
   - **Conviction play** (incl. index-anchor): `--play-type conviction --prediction-reason '...' --thesis-claim '...' --thesis-invalidation '...'` on the BUY — both thesis fields hard-required. For a reallocation sell-down, `--close-reason 'reallocation: funding <ticker> entry'`, sequenced before the dependent BUY in the same tick (`check_order()` re-fetches live account data fresh every call, so the freed cash is visible to the BUY's `gate_cash` check).
   - **Long play**: small, short-horizon (`horizon_days`, currently 3), evidence-gated. Pass `--play-type long --predicted-by-date YYYY-MM-DD --prediction-reason '...' --thesis-claim '...' --thesis-invalidation '...'` (all three plus both thesis fields hard-required). Do not propose a longer horizon yourself — that only changes after Raf reviews hit rate via `signal_scorecard.py --label-horizon long_play_prediction`.
   
   Both play types still have the hard stop apply unconditionally. `gate_long_play`/conviction sizing enforce the caps; a rejection just means fall back to standard, don't retry. Include the play-type tag in the same `--features` JSON you pass to the executor BUY call.

9. **Execute** → via executor (`skills/tool-invocation.md`) if trade — pass `--price`/`--conviction`/`--sector`/`--thesis`/`--features` (score each signal you actually checked, per `skills/self-improving-agent.md`, into the same `--features` JSON from step 8's reconcile call) so the executor's built-in guardrail check (position size, max positions, sector concentration, market hours, conviction floor, bankroll ceiling) can evaluate it; a rejected order exits non-zero with the blocking gate's reason — do not retry the same trade, note it in active.md and move on. For a SELL, also pass `--close-reason` (step 6's breach reason, a thesis break, or a profit-target/MACDh exit — whatever actually triggered it).

   **Sizing `--qty`**: if step 8's fast-path check produced a tier/sizing recommendation, size toward that node's `Sizing guidance` — target utilization of whichever cap applies given the `--play-type` you're using (`risk.max_position_pct` for standard, `risk.conviction_play.position_size_pct` for conviction). Run `python3 scripts/position_sizing.py --tier <tier> --price <price>` to convert that target into a suggested share count rather than estimating by hand — this is an anchor for judgment, not a formula, all the gates above still run unconditionally and can still reject an oversized order exactly as today, and `gate_conviction_play`/`gate_long_play` will now flag (not block) a BUY that lands well under half its tier's target range. No fast-path match → default `probe` sizing (`risk.probe_position_pct`% of portfolio, floor 1 share), same as always.

   **Decision logging is now mechanized**: this same executor call writes the `decisions` table row directly from the `--conviction`/`--thesis`/`--features`/`--sector`/`--close-reason` you already passed it — no separate `record_decision.py decision`/`close` call needed, and no separate outcome-logging step on a closing SELL either (win/loss labeling is already automatic via `close_trade_outcome`). `record_decision.py reconcile` (step 8) is still a separate, required call — it doesn't write anything, it's how you get `combined_confidence` to pass as `--conviction` in the first place.

   For a long play (step 8), also pass `--play-type long --predicted-by-date YYYY-MM-DD --prediction-reason '...'` on the BUY — all three are required together or the executor rejects it outright. Include the long-play tag (`"play_type": "long"`, `"predicted_by_date": "..."`) in the same `--features` JSON you pass to the executor BUY call, so it's on the training_examples row for later review.

   **Position thesis/sector persistence is automatic**: a BUY writes sector/thesis straight into `state/trader.db`'s `positions` row at open time; a SELL closes or trims that same row via the executor call above — no separate file to maintain, nothing to remember to update. `--thesis-claim`/`--thesis-invalidation` (step 8) get the same treatment, plus an entry in `position_thesis_log` for history — unlike the older bare `--thesis` blob (silently overwritten on a scale-in), the log preserves every prior claim even after a later one supersedes it. For a standalone reasoning update not tied to a trade this tick (stop-loss note, conviction shift, catalyst development on a name you're not acting on right now), run `python3 scripts/trader_write.py position-update-thesis --ticker X --thesis '...'` directly — or `--verdict intact|weakening|broken --note '...'` for a thesis re-confirmation (step 6) outside its normal cadence.

   **Writing durable knowledge to the wiki**: `positions.thesis`/`active.md` are this tick's working state, not durable knowledge other sessions or agents can find later. When you reach a real, evidence-backed conclusion worth persisting beyond this tick — a sector thesis, a pattern you've now seen confirmed a few times, something worth not re-deriving from scratch next time — write it with `wiki_apply synthesis "<title>" --body "..." --source-id <id>`, citing the specific evidence it's based on (same discipline as the `--rationale`/`--features` citations above, not just prose). This is occasional, not every tick or every trade. Run `wiki_lint` after writing to catch structural gaps.

10. **Update active.md** → append your current tick entry. Keep it **trim**:
   - 3-5 lines if no trade and no trigger event
   - Include: regime, decisions made, positions near triggers (name + how close, not prices), batch evaluations, scale-in blocks, any operational flags
   - Cite `[tree:<node-id>]` whenever a decision this tick followed or explicitly overrode a `decision_heuristics.md` node — including `Watch`-tier "possible match, no fast-path applied" notes. This is how tree adoption gets verified and how node hit rates get tagged for scoring (`scripts/tree_scorecard.py`).
   - **Do NOT snapshot position data** — no portfolio value, no P&L%, no share counts, no price levels. Those are stale the moment they're written. Query `get_self_stats`/`get_quotes` live when you need them (steps 4, 6).
   - **Rotate on a new trading day**: active.md is read in full every tick, so it must never hold more than one day's entries. Before writing the first `# Current Playbook` title of a new day, move everything currently in active.md into `strategies/active-archive/YYYY-MM-DD.md` (the date of the entries being archived, not today's), then start active.md fresh with just the new title. Never let active.md cross a day boundary un-rotated.

11. **Git commit** → if you modified active.md, commit locally. See `skills/auto-commit.md`.

12. **HEARTBEAT_OK**

## Trim Rules

- No position data in active.md — no portfolio value, no P&L%, no share counts, no prices. Query live instead.
- If this tick is identical to last tick (same regime, no triggers, watchlist unchanged), write "Same as last tick" and done.
- Journal entry at EOD only (nightly maintenance), not per tick.

File map + tool syntax → `TOOLS.md`. Strategy/params → read fresh every tick per step 1, never assumed warm.
